# 小雨面包微信小程序 PRD v1.1

> 文档状态：开发基线稿
> 更新日期：2026-08-13
> 产品形态：微信小程序 + 商家管理后台
> 首发场景：单店、每日鲜制、线上预订、到店自提
> 产品名：`小雨面包`
> 技术路线：银豹式高效点单体验；首发不规划同城配送

---

## 1. 文档目的

本文定义面包店微信小程序首发版本的产品目标、用户、业务范围、完整功能、业务规则、后台能力、数据指标、合规要求、验收标准和版本计划，可用于：

1. 与 SaaS 服务商逐项核对能力和报价；
2. 作为定制开发、视觉设计、测试和验收的统一依据；
3. 约束首发范围，避免开店前被低优先级功能拖延；
4. 为未来多门店、会员运营和生产计划升级保留扩展空间。

## 2. 已知条件与产品假设

当前已确定品牌名为“小雨面包”，首发不规划同城配送。城市、客单价和具体门店地址尚未提供，本文按以下合理假设设计：

- 首发为一家直营网点；
- 主营现烤面包、甜点、饮品及礼盒，部分商品每日限量；
- 顾客可以当天或提前下单；
- 首发唯一履约方式为预约到店自提；
- 支付方式以微信支付为主；
- 门店需要在手机、平板或电脑上接单，并可连接小票打印机；
- 库存必须体现“某日、某时段是否还能卖”，不能只维护一个长期总库存；
- 蛋糕定制、储值、复杂分销、多门店调拨不进入首发 MVP。

在立项评审时，应由经营负责人确认其余假设。同城配送不进入当前产品架构、开发范围或供应商验收范围；未来若经营策略变化，应单独立项。

## 3. 市场与可复用方案调研

### 3.1 微信原生基础能力

微信生态可以提供小程序入口、微信登录、微信支付、订阅消息和客服等基础能力，但商品、鲜食库存、生产、退款和门店运营仍需要 SaaS 或自建业务系统承载。

交易类小程序在正式支付接入时还需满足交易规范和订单发货管理要求。微信支付官方文档明确提示：交易类小程序需要按规范接入订单发货管理，否则支付能力可能受限。

### 3.2 餐饮/烘焙 SaaS

| 方案 | 已公开能力 | 更适合 | 主要局限/核验项 |
|---|---|---|---|
| 银豹烘焙/点餐小程序 | 烘焙收银、预约点单、自提、会员、进销存、供应链、开放 API；预约区间可细到 10 分钟 | 单店或连锁烘焙，重视线下收银、库存和小程序一体化 | 聚合小程序模板定制空间有限；需核验独立 AppID、数据导出、接口和套餐报价 |
| 有赞门店/连锁 | 小程序点单页支持外卖、自提、堂食扫码；有烘焙行业方案、库存、会员和营销能力 | 重视品牌装修、私域营销、优惠活动和快速上线 | 需要至少一家有赞网店；套餐、插件、POS 和实际报价需核验 |
| 客如云 | POS、会员、预点餐、预定自提、报表；开放平台支持自研小程序接入 POS/CRM | 已采用餐饮 POS，或计划较强的门店数字化与系统集成 | 更偏泛餐饮；需专项验证烘焙日库存、生产看板和商品预售能力 |
| 微盟智慧餐饮 | 堂食、会员外卖、商城、会员和多平台订单聚合 | 有多渠道经营、私域会员和连锁规划的品牌 | 对单店首发可能偏重；具体版本、实施周期和总成本需商务确认 |

调研与经营决策结论：小雨面包采用银豹路线，优先保证线下收银、鲜食库存、预约自提、生产出单与核销效率。最终采购仍须经过真实商品、真实时段库存、真实退款和真实小票的完整试单。

### 3.3 开源可二开方案

| 项目 | 技术/许可 | 可复用范围 | 风险判断 |
|---|---|---|---|
| 芋道商城 `yudao-mall-uniapp` | Vue 3 + uni-app，后端支持 Spring Boot/Cloud，MIT | 商品、SKU、订单、支付、会员、优惠券、营销、管理后台 | 通用商城能力完整，但需要新增鲜食日期库存、取货时段容量、生产看板和门店打印 |
| ShopXO uni-app | uni-app + ShopXO 后端，MIT | 多端商城、商品、订单、后台、DIY | 适合通用零售商城二开；烘焙履约仍需定制和代码审计 |
| CoreShop | uni-app + ASP.NET Core；允许自运营商用但需保留版权，限制再发行 | 商品、订单、库存、门店核销、优惠券、退款、打印、报表 | 功能较全，但许可不是标准宽松开源许可；技术栈和版权约束需先接受 |
| `woniudiancang/bee` | 原生微信小程序，依赖外部 API 服务 | 点餐、外卖、扫码点餐原型 | 对第三方 API 和后台依赖较强；在数据归属、稳定性、安全审计完成前不建议直接作为生产底座 |

调研结论：开源项目可以复用通用商城骨架，无法直接替代烘焙门店系统。若团队已有 Java/Vue 能力，芋道商城是更适合评估的自研底座；若开店时间紧，首发自研的交付风险明显高于成熟 SaaS。

### 3.4 推荐落地路线

**推荐：SaaS 首发 + 数据可迁移设计。**

1. 用本文 P0 清单要求银豹完成现场演示与书面答复；
2. 完成 7 天真实试运行，覆盖商品上架、库存、支付、取消、退款、自提、打印和日结；
3. 小程序主体、AppID、微信支付商户号和结算账户由面包店自己持有；
4. 合同中写明订单、商品、会员、库存数据的导出格式和终止服务后的迁移安排；
5. 当出现多门店生产调拨、订阅制面包、自有复杂排产等差异化需求时，再启动定制开发。

## 4. 产品愿景与目标

### 4.1 产品愿景

让顾客在到店前完成“选商品—确认有货—选择时间—支付”，让门店提前知道“何时做、做多少、交给谁”，减少排队、缺货、错单和电话沟通。

### 4.2 首发目标

- 顾客 3 分钟内完成一次常规下单；
- 顾客下单时能看到准确的可售日期、时段和库存状态；
- 门店在一个工作台处理线上订单，并按预约取货时间组织生产；
- 支持完整的支付、取消、退款、通知和售后闭环；
- 上线后可量化查看订单量、销售额、客单价、热销商品和复购表现。

### 4.3 建议业务指标

以下为上线后 30 天的建议目标，最终数值需结合客流和城市情况校准：

| 指标 | 口径 | 建议目标 |
|---|---|---:|
| 浏览到支付转化率 | 支付用户数 / 商品详情访问用户数 | ≥ 8% |
| 支付成功率 | 支付成功订单 / 发起支付订单 | ≥ 98%（剔除用户主动放弃） |
| 超卖率 | 支付后因缺货取消的商品件数 / 已支付商品件数 | ≤ 0.2% |
| 准时备妥率 | 承诺取货时间前进入“待取货”的订单 / 应履约订单 | ≥ 95% |
| 订单差错率 | 错货、漏货、规格错误订单 / 完成订单 | ≤ 0.5% |
| 退款处理时效 | 退款申请至门店首次处理 | 营业时间内 ≤ 2 小时 |
| 30 日复购率 | 首单后 30 日再次支付的用户 / 首购用户 | ≥ 20% |

### 4.4 本期不以此为目标

- 替代专业财务软件；
- 自建骑手调度平台；
- 搭建第三方商户入驻平台；
- 首发即支持全国快递、加盟商结算或中央工厂 ERP；
- 依靠复杂裂变玩法获取大量陌生流量。

## 5. 用户与角色

| 角色 | 核心诉求 | 主要权限 |
|---|---|---|
| 顾客 | 快速找到想吃的商品，确认有货，按时拿到 | 浏览、下单、支付、取消、退款、查看订单、联系客服 |
| 店员/收银员 | 快速接单、打印、核销，处理现场异常 | 查看订单、接单、改履约状态、核销、备注、发起售后 |
| 烘焙/生产人员 | 清楚知道每个时间段要做什么和做多少 | 查看生产汇总、标记制作中/已备妥、上报缺货 |
| 店长 | 控制商品、库存、时段、履约、退款和当日经营 | 商品、库存、订单、退款、营销、报表管理 |
| 系统管理员 | 管理账号、权限、支付和系统配置 | 全部配置、角色授权、日志查看、数据导出 |
| 客服（可由店长兼任） | 查询问题、联系顾客、闭环售后 | 订单查询、退款审核、客服备注、售后记录 |

## 6. 核心场景与用户故事

### 6.1 顾客场景

1. 作为顾客，我希望看到今天和未来可预订的商品，避免付款后才知道售罄。
2. 作为顾客，我希望选择可用的预约自提时段，并在付款前看到完整费用。
3. 作为顾客，我希望在商品详情看到口味、规格、原料提示、过敏原、保存方式和最佳食用时间。
4. 作为顾客，我希望微信支付后立即收到结果，并在接单、备妥和完成等节点收到通知。
5. 作为顾客，我希望在允许的时间内自主取消，超出时间后能提交退款申请并联系门店。
6. 作为老顾客，我希望能快速复购历史商品，并使用优惠券或会员权益。

### 6.2 门店场景

1. 作为店员，我希望新订单自动提醒并打印，避免漏单。
2. 作为生产人员，我希望按取货时间汇总商品数量，减少逐单翻看。
3. 作为店长，我希望临时停售商品、调整某日库存或关闭某个时段。
4. 作为店长，我希望一眼识别即将超时、退款、缺货和顾客备注订单。
5. 作为店长，我希望核销码只能成功使用一次，并保留操作人和时间。
6. 作为经营者，我希望每天查看销量、销售额、退款、折扣、渠道和商品排行。

## 7. 版本范围与优先级

### 7.1 P0：开业必须具备

- 微信授权与手机号快捷填写；
- 首页、分类、搜索、商品详情、规格选择、购物车；
- 按日期/时段的可售库存；
- 预约到店自提；
- 自提日期、时段、容量和最晚下单时间校验；
- 订单确认、优惠、微信支付、支付结果；
- 订单列表/详情、取消、退款申请、再次购买；
- 订阅消息、客服电话/微信客服；
- 自提码/核销码；
- 商家商品、库存、时段、订单、生产、退款和报表后台；
- 新单提醒、小票打印、操作日志；
- 主体资质、隐私政策、用户协议、售后规则展示；
- 埋点、监控、备份和数据导出。

### 7.2 P1：上线后 1–2 个迭代

- 会员积分、等级、会员价；
- 新人券、满减券、商品券、券包；
- 收藏、常购清单、缺货到货提醒；
- 商品评价与门店回复；
- 定制蛋糕预约（尺寸、夹心、题字、图片、交付日期、定金/尾款）；
- 电子发票；
- 精细化人群标签和复购提醒；
- 经营日报、库存预警和损耗记录。

### 7.3 P2：规模化阶段

- 多门店选择、跨店库存与订单；
- 中央厨房排产、门店要货和调拨；
- 面包周订阅/月订阅；
- 企业团购和大客户账期；
- 礼品卡、储值卡和家庭共享权益；
- 视频号、公众号、抖音、美团等渠道统一商品和订单；
- 智能补货、销量预测和个性化推荐。

储值、预付卡、分销和自动续费涉及额外合规、资金与退款复杂度，应独立立项评审。

## 9. 顾客端详细需求

### 9.1 门店与营业状态

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| C-001 | 展示门店名称、地址、电话、营业时间 | 支持一键导航和拨号；闭店时仍可浏览未来可预订商品 |
| C-002 | 展示营业状态 | 至少包括营业中、休息中、今日售罄、临时闭店、可预订 |
| C-003 | 展示最近可履约时间 | 确认订单页展示并选择可履约时段；时段变化后实时重新校验 |

### 9.2 首页、分类与搜索

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| C-010 | 首页运营位 | 支持轮播图、公告、分类入口、热销、新品和活动组件 |
| C-011 | 商品分类 | 支持面包、蛋糕甜点、三明治、饮品、礼盒等后台自定义分类 |
| C-012 | 商品搜索 | 支持商品名、别名和关键词；无结果时展示推荐商品 |
| C-013 | 排序与筛选 | 可按推荐、销量、价格排序；可筛选今日可取、素食等标签 |
| C-014 | 售罄状态 | 售罄商品保留展示并明确标识，不允许加入当前日期购物车 |

### 9.3 商品详情

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| C-020 | 基础信息 | 图片、名称、短描述、售价、划线价（若有）、单位、销量、库存状态 |
| C-021 | SKU 规格 | 支持尺寸、口味、数量、加料等规格；价格和库存随规格变化 |
| C-022 | 鲜食信息 | 展示主要原料、过敏原、净含量/规格、保存方式、保质/最佳食用时间 |
| C-023 | 可售日期/时段 | 点单阶段展示今日可售状态；自提日期与时段在确认订单页选择，只展示购物车商品均有库存且有容量的时段 |
| C-024 | 购买限制 | 展示起购量、限购量、提前预订时间和不可取消时间 |
| C-025 | 分享 | 支持分享商品卡片；被分享者进入后重新校验价格和库存 |

过敏原至少支持配置：含麸质谷物、蛋、乳、花生、坚果、大豆等。页面应提示“实际生产环境可能存在交叉接触”，具体文案由食品安全负责人审核。

### 9.4 购物车

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| C-030 | 加购与数量修改 | 达到库存或限购上限时不可继续增加，并明确原因 |
| C-031 | 履约上下文 | 购物车绑定门店；进入确认订单页后绑定自提日期与时段，选择或切换时重新校验全部商品 |
| C-032 | 失效商品 | 价格、库存或时段变化时标出失效项，不静默删除 |
| C-033 | 金额明细 | 展示商品小计、包装费、优惠和应付金额 |
| C-034 | 结算校验 | 服务端再次校验价格、库存、营业状态、时段容量和优惠券 |

### 9.5 订单确认

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| C-040 | 履约方式 | 首发固定为到店自提，不展示配送入口 |
| C-041 | 自提信息 | 选择自提日期和时段，填写取货人手机号，可选备注 |
| C-043 | 优惠选择 | 自动推荐最优可用券，允许顾客手动切换；展示不可用原因 |
| C-044 | 订单备注 | 提供预设标签和文字备注；提示备注不等于门店承诺 |
| C-045 | 协议确认 | 首次下单确认用户协议、隐私政策、售后与取消规则 |
| C-046 | 提交防重 | 重复点击只生成一张订单；返回唯一订单号 |

### 9.6 支付

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| C-050 | 微信支付 | 使用门店自有商户号；金额以服务端订单为准 |
| C-051 | 库存预占 | 提交订单后预占库存，默认 10 分钟未支付自动关闭并释放 |
| C-052 | 支付结果确认 | 以前后端查单结果为准，不能只依赖小程序端回调 |

## 10. 商家后台详细需求

### 10.1 今日看板

- 今日支付订单数、销售额、退款额、客单价；
- 待接单、即将超时、制作中、待取货、售后数量；
- 按未来 30/60/120 分钟显示生产压力；
- 热销、售罄、低库存和异常订单提醒；
- 数据按角色脱敏，普通员工不查看完整经营报表。

### 10.2 订单中心

| 编号 | 需求 | 规则/验收 |
|---|---|---|
| M-010 | 新单提醒 | 声音、弹窗、角标，可联动云打印；失败自动重试并告警 |
| M-011 | 接单/拒单 | 拒单必须选择原因；已支付拒单自动进入退款流程 |
| M-012 | 状态处理 | 接单、制作中、已备妥、已核销/完成；按权限操作 |
| M-013 | 查询筛选 | 订单号、手机号后四位、自提码、状态、日期、履约方式、商品 |
| M-014 | 订单备注 | 区分顾客备注、客服备注、生产备注；记录操作者和时间 |
| M-015 | 改期 | 联系顾客并取得确认后修改；重新校验库存/容量并保留变更前后值 |
| M-016 | 导出 | 按时间和权限导出订单；手机号、地址默认脱敏 |

### 10.3 生产看板

- 按“履约日期 → 时间段 → 商品/SKU”汇总待制作数量；
- 可切换逐单视图和商品汇总视图；
- 区分已付、已接单、制作中、已完成、取消；
- 支持打印生产单、拣货单和订单小票；
- 商品上报缺货后，列出受影响订单并启动逐单处理；
- 支持按岗位或工位筛选，例如面包、裱花、饮品、打包；
- 生产人员不能修改订单金额或执行退款。

### 10.4 商品与 SKU

- 分类、商品、SKU、价格、图片、标签、上下架和排序；
- 商品原料、过敏原、保存方式、保质/最佳食用时间；
- 支持永久停售、临时停售和指定日期停售；
- 支持提前预订天数、最短提前时间、起购/限购、可履约方式；
- 修改已售订单不追溯，订单保存购买时快照；
- 调价需记录操作者、时间、旧值和新值。

### 10.5 日期库存与时段容量

这是烘焙场景的核心模块：

- 库存维度至少为“门店 + 履约日期 + SKU”；必要时扩展到时段；
- 可批量生成未来 7/14/30 天计划库存；
- 支持基础日历模板、节假日覆盖和临时增减；
- 支持安全库存、售罄、超卖保护和低库存提醒；
- 自提可设置各时段最大订单数或最大商品件数；
- 支付预占、支付成功扣减、取消/退款释放均需原子化处理；
- 后台人工改库存不得造成已支付订单失效；
- 所有库存调整必须有原因和审计记录。

### 10.6 自提管理

- 配置自提地址、导航点、联系电话、营业日历；
- 配置每个时段长度、容量、最晚下单时间；
- 扫码或输入码核销；
- 核销时展示订单摘要并二次确认；
- 重复核销明确提示原核销时间和操作人；
- 支持店员在获得授权后撤销误核销，并记录日志。

### 10.7 退款与售后

- 配置不同商品的自动取消截止时间；
- 退款审核展示订单、支付、优惠、生产状态和历史沟通；
- 支持全额、部分、仅商品、商品加相应费用等退款方式；
- 退款金额不得超过原实付金额；
- 微信退款接口超时使用相同退款单号重试，禁止重复退款；
- 每个售后单保留申请、审核、支付渠道结果和客服备注。

### 10.8 会员与营销

P0 只需要识别顾客、记录消费和使用基础优惠券；P1 再启用积分与等级。

- 优惠券支持新人券、满减券、商品券；
- 配置有效期、门槛、适用商品、适用时段、发放量和每人限领；
- 服务端计算优惠并防止重复核销；
- 退款时按实际规则退券或作废，页面提前说明；
- 禁止将营销授权与完成下单绑定；
- 群发触达前确认用户授权和平台规则。

### 10.9 账号与权限

- 角色至少包括系统管理员、店长、客服、店员、生产人员；
- 权限覆盖页面、按钮和数据范围；
- 高风险操作包括退款、调价、库存调整、导出和权限修改；
- 管理员开启双重验证或至少使用强密码与登录设备校验；
- 离职账号即时停用；
- 日志包含操作者、时间、IP/设备、对象、变更前后值和结果。

### 10.10 报表

- 日/周/月销售额、支付订单、退款、折扣、客单价；
- 按商品、SKU、分类、时间段排行；
- 新老顾客、复购率、优惠券使用情况；
- 售罄时间、缺货取消、生产准时率、退款原因；
- 支持 CSV/XLSX 导出；金额口径需明确包含/排除退款和优惠。

## 11. 核心业务规则

### 11.1 订单状态机

主订单状态建议如下：

`待支付 → 已支付/待接单 → 已接单 → 制作中 → 待取货 → 已核销/完成`

异常分支：

- 待支付 → 已关闭；
- 已支付/待接单 → 已取消/退款中 → 已退款；
- 已接单/制作中/待取货 → 售后处理中 → 部分退款或已退款；
订单状态、支付状态、退款状态和生产状态应分字段保存，避免一个状态枚举承载全部情况。

### 11.2 库存与容量

1. 顾客提交订单后预占库存和时段容量 10 分钟；
2. 支付成功后确认占用；超时关闭后释放；
3. 同一 SKU 的扣减必须由服务端原子执行；
4. 退款是否回补库存取决于生产阶段和剩余可售时间，由规则或店长决定；
5. 时段满额时可展示相邻可用时段；
6. 临时闭店必须阻止新订单，但不能隐藏未完成订单；
7. 前端展示库存仅供交互，服务端结果为最终依据。

### 11.3 时间规则

- 后台统一按 `Asia/Shanghai` 保存和展示经营日期；
- 数据库存储时间戳，界面明确显示门店本地时间；
- 每个商品可配置最短提前量，例如普通面包 30 分钟、整蛋糕 24 小时；
- 门店自提可配置最晚下单时间；
- 节假日营业、库存和时段可覆盖常规模板；
- 规则修改只影响新订单，已支付订单按下单快照履约。

### 11.4 价格与优惠

- 订单保存商品标价、SKU 加价、包装费、优惠和实付快照；
- 前端不得自行决定最终价格；
- 同一订单 P0 只使用一张店铺券，是否叠加会员价在 P1 明确；
- 划线价必须有真实依据；
- 任何必付费用在提交订单前完整展示。

### 11.5 取消规则建议

- 未支付：随时取消；
- 普通现货：门店接单前可自动取消并原路退款；
- 已开始制作：转人工审核；
- 定制商品：按页面明确的截止时间和定金规则处理；
- 因门店缺货或临时闭店导致无法履约：顾客可选择改期、替换或退款，门店承担相应责任；
- 规则须在商品页和结算页可见，且订单保存当时版本。

## 12. 关键流程

### 12.1 自提订单

1. 顾客进入小程序，首发履约方式固定为到店自提；
2. 浏览商品并加入购物车；
3. 进入确认订单页，通过时间滚轮选择日期/时段；
4. 服务端按购物车和所选时段重新校验库存与容量；
5. 提交订单并预占 10 分钟；
6. 微信支付成功，门店收到提醒/小票；
7. 门店接单，生产人员按时段制作；
8. 标记已备妥，顾客收到通知；
9. 顾客到店出示自提码；
10. 店员核销并交付，订单完成。

### 12.2 缺货处理

1. 店员上报某 SKU 缺货；
2. 系统立即停止该日期/时段继续销售；
3. 列出所有受影响的未完成订单；
4. 店员逐单联系顾客；
5. 顾客选择替换、改期、部分退款或整单退款；
6. 后台记录顾客选择、处理人和资金结果；
7. 经营报表计入“缺货异常”。

## 15. 非功能需求

### 15.1 性能

- 首页首屏在常见 4G/5G 网络下目标 ≤ 2 秒可交互；
- 商品列表翻页和购物车操作目标响应 ≤ 1 秒；
- 提交订单、支付查单等关键接口 P95 ≤ 2 秒；
- 图片使用压缩、懒加载和 CDN；
- 高峰容量至少按预计峰值的 3 倍压测。

### 15.2 可用性与可靠性

- 月可用性目标 ≥ 99.9%（SaaS 以合同 SLA 为准）；
- 支付、退款、库存扣减、回调处理必须幂等；
- 打印失败不能改变订单状态，需告警和人工补打；
- 核心订单数据库每日备份，并定期验证恢复；
- 系统故障时后台能导出未完成订单，门店具备纸面/电话应急流程。

### 15.3 安全

- AppSecret、支付密钥和证书只存服务端密钥系统；
- 全链路 HTTPS；
- 后台最小权限、登录保护、操作审计；
- 服务端校验价格、权限、库存和状态流转；
- 防止重复支付、重复退款、越权查单、核销码穷举和接口重放；
- 上传图片限制类型、大小并进行安全检测；
- 定期更新依赖并处理高风险漏洞。

### 15.4 隐私

- 浏览阶段不强制登录或获取手机号；
- 手机号在填写取货人信息时取得授权；首发不申请位置权限；
- 隐私指引列明信息类型、目的、保存期限、第三方 SDK 和联系方式；
- 拒绝非必要授权时仍可使用不依赖该权限的功能；
- 后台访问个人信息有权限和审计；
- 提供更正、删除、注销和投诉渠道。

### 15.5 易用性

- 主要按钮适合单手操作，价格和状态清晰；
- 不以颜色作为唯一状态提示；
- 错误提示说明原因和可执行下一步；
- 门店后台在手机和平板上可完成接单、出单、核销和退款；
- 顾客下单主路径不超过 6 个关键动作。

## 16. 合规与上线前置

以下内容需结合门店所在地和实际经营品类由专业人员确认：

1. **经营主体**：使用企业或个体工商户主体注册小程序，主体名称与实际经营一致；
2. **小程序备案**：境内提供互联网信息服务的小程序需先履行备案手续，并在显著位置展示备案编号；
3. **食品资质**：按经营方式取得并展示有效的食品经营相关许可/备案；自制裱花蛋糕、预包装食品、现场制售等可能对应不同要求；
4. **微信类目与审核**：选择与实际业务一致的餐饮/食品类目，提交平台要求的许可证材料；
5. **微信支付**：申请并绑定自有商户号，开通小程序支付，配置退款和发货信息管理；
6. **网络餐饮责任**：展示经营者和许可信息，保证线上信息真实，并按适用规定留存订单和交易记录；2026 年发布的相关规定要求平台和通过自建网站提供餐饮服务的经营者将网络餐饮订单信息自交易完成起至少保存三年；
7. **消费者权益**：明确价格、费用、履约、取消、退款、投诉和客服方式；
8. **个人信息保护**：提供小程序隐私保护指引，在调用手机号等隐私接口前完成必要告知与同意；
9. **内容真实性**：图片、划线价、销量、原料、净含量、保质期和宣传用语真实可核验；
10. **第三方责任**：与 SaaS、打印、短信等供应商签署适当的数据和服务协议。

本文为产品设计要求，不替代针对门店所在地和具体食品品类的法律意见。

## 17. 数据埋点与指标口径

### 17.1 核心事件

`app_open`、`store_view`、`search`、`product_view`、`sku_select`、`add_to_cart`、`checkout_view`、`slot_select`、`coupon_select`、`order_submit`、`pay_start`、`pay_success`、`pay_fail`、`order_cancel`、`refund_apply`、`refund_success`、`order_ready`、`order_verified`、`reorder_click`、`customer_service_click`。

### 17.2 公共属性

- user_id（匿名化）；
- store_id；
- session_id；
- source/scene；
- order_id（内部匿名标识）；
- product_id/SKU；
- business_date/slot；
- app_version；
- event_time。

埋点不得记录完整手机号、地址、支付凭证、聊天内容或其他非分析所需的个人信息。

## 18. P0 验收标准

### 18.1 主链路

1. 顾客可在未登录状态浏览商品；
2. 登录后可完成选品，并在确认订单页选择自提时段、结算和微信支付；
3. 支付后门店后台 10 秒内可看到订单并触发提醒；
4. 门店可接单、制作、备妥、核销，顾客端状态同步；
5. 订单全部费用在支付前可见，支付金额与订单金额一致；
6. 自提码重复使用被拒绝并留痕。

### 18.2 库存与并发

1. 同一 SKU 仅剩 1 件时，两名顾客并发提交最多一人成功；
2. 待支付超时后库存与时段容量自动释放；
3. 前端旧页面提交时，服务端能拦截失效价格、库存和时段；
4. 后台停售后，顾客端刷新即不可继续购买；
5. 已支付订单不会因后续调价或停售而改变快照。

### 18.3 支付与退款

1. 支付成功回调重复到达不会重复记账；
2. 顾客支付后关闭页面，再进入可看到正确订单；
3. 自动取消能发起原路退款；
4. 退款接口超时重试不会产生重复退款；
5. 部分退款后订单金额、退款金额和报表口径一致。

### 18.4 异常与降级

1. 打印机断网时订单仍可接收，后台显示打印失败并可补打；
2. 订阅消息失败不影响订单；
3. 管理员可导出全部未完成订单用于应急履约。

### 18.5 权限与隐私

1. 生产人员无法查看完整手机号或执行退款；
2. 普通店员无法改价、导出会员或修改角色；
3. 小程序不申请非必要位置权限；
4. 隐私政策、用户协议、资质和客服入口可访问；
5. 注销请求有明确流程，依法需保留的订单数据与日常账号访问隔离。

## 19. 上线计划

以成熟 SaaS 为基础的建议节奏：

| 阶段 | 周期 | 输出物/退出条件 |
|---|---:|---|
| 业务确认与选型 | 3–5 天 | 确认经营方式、资质、P0 清单、两家演示、报价与合同关键条款 |
| 账号与基础配置 | 3–7 天 | 主体、AppID、商户号、门店、自提时段、支付、打印、员工权限 |
| 商品与视觉内容 | 5–10 天，可并行 | 商品图、规格、原料/过敏原、价格、库存、首页装修和协议 |
| 全链路测试 | 3–5 天 | 自提/支付/退款/打印/库存/消息全部通过 |
| 备案与平台审核 | 以平台实际进度为准 | 备案、类目资质、隐私配置、代码审核通过 |
| 试营业 | 7 天 | 真实订单运行，超卖、漏单、退款和打印问题闭环 |
| 正式上线 | 1 天 | 运营、客服、生产、技术应急联系人和回滚方案就绪 |

定制开发通常还需 UI、前后端开发、接口联调、安全测试和运维建设，应单独估时，不建议以 SaaS 配置周期承诺。

## 20. 成本评估框架

询价时要求供应商拆分以下项目，避免只比较软件年费：

- 小程序/SaaS 版本费；
- POS、平板、扫码枪、打印机等硬件；
- 支付通道费率和结算规则；
- 短信、存储、CDN、打印服务；
- 会员、营销、进销存、API 等增值模块；
- 小程序装修、上架、培训、数据初始化和现场实施；
- 定制开发、接口联调和后续维护；
- 第二年续费、版本升级和退出/数据迁移成本。

供应商报价变化较快，本文不写未经书面确认的固定价格。

## 21. SaaS 选型打分表

建议总分 100 分，任何“红线项”不通过即淘汰。

| 维度 | 权重 | 核验方式 |
|---|---:|---|
| 鲜食日期库存、预占和防超卖 | 20 | 两个账号并发抢最后 1 件真实测试 |
| 自提时段、容量、提前量与最晚下单规则 | 15 | 配置多个时段、满额、改期、临时关闭和超时 |
| POS/打印/生产看板 | 10 | 完整下单到出单、汇总制作、补打 |
| 支付、取消、部分退款 | 10 | 小额真实支付和全额/部分退款 |
| 商品、过敏原、预订规则 | 8 | 上架 5 类典型商品和多规格商品 |
| 品牌装修与顾客体验 | 8 | 用品牌素材完成首页和下单主路径 |
| 数据归属、导出与开放 API | 10 | 导出样例、接口文档、合同条款 |
| 稳定性、安全、备份、SLA | 8 | 提供 SLA、故障记录和恢复机制 |
| 实施、培训与售后 | 6 | 明确响应人、时间和服务边界 |
| 三年总成本 | 5 | 汇总全部软件、硬件、交易和服务费用 |

红线项：

- 小程序主体、商户号或结算账户不能由面包店掌握；
- 订单、会员、商品数据无法完整导出；
- 无法完成真实退款或库存防超卖；
- 关键费用、续费或终止条款不透明；
- 无法提供食品类目入驻所需的合规配合。

## 22. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 开业日期早于备案/审核完成 | 无法按期上线 | 资质、备案和支付申请优先启动；保留门店收银和电话预订方案 |
| 线上库存与现场库存不一致 | 超卖、退款、差评 | POS 一体化；线上库存池、安全库存、日清和盘点 |
| 高峰漏单或打印失败 | 履约超时 | 多端提醒、打印重试、未接单告警和人工订单看板 |
| SaaS 锁定 | 迁移困难 | 自持账号，合同约定 API、数据导出和退出迁移 |
| 功能堆积拖延上线 | 错过开业窗口 | 严格 P0/P1/P2；首发暂缓储值、分销、订阅、多门店 |
| 食品信息或宣传不准确 | 合规与信任风险 | 食品安全负责人审核原料、过敏原、保质和宣传文案 |
| 顾客备注未被执行 | 客诉或过敏风险 | 预设选项与自由备注分开；特殊要求必须人工确认 |

## 23. 待经营负责人确认的问题

这些问题不会阻止先选型，但必须在最终视觉和系统配置前确认：

1. 门店城市、具体地址和计划开业日；
2. 每日营业时间、取货时段粒度和峰值订单量；
3. 商品类型、平均 SKU 数、是否有饮品和定制蛋糕；
4. 普通面包和定制商品分别提前多久预订、何时不可取消；
5. 是否已经采购 POS、打印机、进销存或会员系统；
6. 是否首发会员积分/优惠券，是否暂缓储值；
7. 小程序主体、食品许可、备案和微信支付商户号准备情况；
8. 品牌视觉素材、商品图片、原料/过敏原资料由谁负责；
9. 门店每天由谁维护库存、谁接单、谁审核退款；
10. 顾客服务电话、服务时段和客诉升级负责人。

## 24. 评审结论建议

当前建议批准以下决策：

1. P0 按“小雨面包”单店、预约到店自提设计，不规划同城配送；
2. 首发采用银豹式高效点单路线，优先验证银豹烘焙；
3. 使用本文验收清单进行真实试单，产品演示不能替代验收；
4. 主体、AppID、商户号、结算账户和数据导出权归面包店；
5. 储值、定制蛋糕、多门店和复杂营销进入后续版本；
6. 本文已形成 v1.1 开发基线，剩余经营参数确认后进入银豹试用和正式小程序工程化。
